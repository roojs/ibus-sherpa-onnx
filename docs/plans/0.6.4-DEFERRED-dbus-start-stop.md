# 0.6.4 DEFERRED D-Bus Start / Stop

ℹ️ No current use case — deferred. IBus-as-tool start path effectively rejected; a later D-Bus API could still make sense for apps that manage their own I/O.

Parent: [`0.4-DONE-prefs-feedback-models.md`](0.4-DONE-prefs-feedback-models.md)

## What we tried / why IBus start is a poor fit

ℹ️ Starting dictation **through IBus** (hotkey / panel / injecting into the focused context) hit hard **focus** problems: the engine only commits into the focused input context, and stealing or synthesizing focus for a host “mic button” was unreliable.

ℹ️ Preferences got around “start listening into this entry” by using **AT-SPI (a11y)** to synthesize the toggle hotkey while the phrase `Gtk.Entry` already had focus — that is a prefs-only workaround, not a general app API.

ℹ️ Engine behaviour now commits spoken text into the focused field more readily (preedit commit mode / quicker endpoint commits). For ordinary IBus use, a separate Start/Stop control is **not clearly needed** right now.

## What is still reasonable

🔷 Allow a **session D-Bus** Start / Stop API so a host app can start recording **from outside** IBus and **manage the I/O / document content itself** (copy results where it wants).

ℹ️ That path is **not** “use Sherpa as a normal IBus tool remotely.” Focus nature of IBus means you cannot reliably drive another app’s text field via the engine without that field being focused. D-Bus Start/Stop is for apps that own their UI and treat the recognizer as a service.

## Non-goals (current)

🚫 Treating D-Bus Start as a drop-in replacement for the IBus hotkey into arbitrary focused widgets.
🚫 AT-SPI / ydotool as the product Start/Stop for host apps.
🚫 Engine commit into unfocused / background windows.
🚫 Shipping this as required for 0.6.1 voice commands (already DONE without it).

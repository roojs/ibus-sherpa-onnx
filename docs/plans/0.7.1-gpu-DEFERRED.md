# 0.7.1 GPU / provider DEFERRED

**Status:** DEFERRED

**ℹ️** Split out of the old combined “Paraformer + GPU” draft. Orthogonal to Cantonese / Paraformer — see [`0.7-streaming-paraformer-cantonese.md`](0.7-streaming-paraformer-cantonese.md).

## Purpose (if revived)

- **🔷** Optional non-CPU `provider` when the installed `libsherpa-onnx` + ONNX Runtime build supports it; otherwise stay on CPU.
- Today [`Transcriber.vala`](../../src/Transcriber.vala) hardcodes `provider = "cpu"`. C API already documents `"cpu"`, `"cuda"`, `"coreml"`.

## Why deferred

- **ℹ️** Research so far suggests we would **not** gain much from GPU for our streaming ASR path on typical desktop loads.
- **ℹ️** If we ever care about acceleration, interest is in **Vulkan**, not CUDA — we do not have many NVIDIA cards around.
- **ℹ️** Packaging is the hard part regardless: consumer `libsherpa-onnx-c-api` builds are almost certainly **CPU ORT**.

## Notes (parked design)

### Runtime (sketch)

- Resolve provider once at `load()`: prefer accelerated EP if usable, else `cpu`.
- Optional prefs/settings override: `general/provider=` `auto` | `cpu` | … (default `auto`).
- Silent, reliable fallback to CPU when the `.so` or device is missing.
- Same provider field for transducer and Paraformer (both go through ORT).

### Packaging / EP choice

- **🚫** Do not `Depends:` on a full CUDA toolkit in the IBus `.deb`/`.rpm` by default.
- **💩** Prefer investigating **Vulkan** EP / builds over CUDA if this leaves DEFERRED.
- **💩** Confirm whether int8 Paraformer/Nemotron on any GPU EP is actually faster/stable before advertising it.
- **💩** Probe strategy + whether [roojs/sherpa-onnx releases](https://github.com/roojs/sherpa-onnx/releases) ever ship a non-CPU package in the same train.

## Non-goals while DEFERRED

- **🚫** Blocking 0.7 Cantonese / Paraformer on provider work.
- **🚫** Shipping CUDA as the advertised acceleration story.
